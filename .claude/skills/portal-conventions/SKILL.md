# Portal conventions

Docs: `../../docs/index.md` (layer docs). Layer rules: see the sibling skills `pages`, `api-routes`, `components`, `lib`, `request-gate` and `e2e`. The root `CLAUDE.md` summarises these project rules.

> Next.js here is 16.x with breaking changes from older versions. Check `node_modules/next/dist/docs/` before writing framework-level code. The request gate is `proxy.ts` (not `middleware.ts`).


- Import with the `@/` alias (`@/lib/session`, `@/components/NavBar`), not long relative paths.
- **Every screen must be responsive.** It has to fit and stay usable from a 320px Samsung/iPhone up to a wide desktop: fluid widths
  (no fixed widths wider than the screen), text that wraps, touch targets of at least 44px, and wide tables inside `.table-wrap`.
  Check it by adding the route to `e2e/mobile.spec.ts`, which fails on sideways overflow on iPhone and Samsung profiles.
- **Daily request limit (backend 429, "Daily request limit exceeded for customer N: max 1000 requests per day").** Show it ONLY as the
  one-time pop-up `RateLimitNotice`, when the limit is first exceeded: not on every request or page load while it stays exceeded
  (`lib/rate-limit.ts` remembers it per tab until a request succeeds again). NEVER show it as a red inline message on any screen:
  `ErrorMessage` swaps it for a short grey "This isn't available right now" note (so a screen is never just blank), so always render API errors through `ErrorMessage`, never your own `<p className="error">{message}</p>`.
  The Help entry `/help#request-limit` explains it.
- Match the surrounding code: naming, comment density, plain CSS classes from `app/globals.css`.
- Never write passwords, security answers or tokens to a log, the console, an error message or a response body.
- Tunables are env vars, documented in `.env.local.brite`. Text that quotes them (`lib/faq.ts`, `lib/legal.ts`)
  must read the same variable, so the wording cannot drift from behaviour.
- Identity belongs to the Spring backend (customer and employee logins, JWTs, privileges). The portal keeps the token in an
  httpOnly cookie and never decides permissions itself; do not re-add a local user store, 2FA, audit log or `.data/` state.
- Only go through the backend's BFF endpoints; never access its database directly.
- Call the backend only when needed: every call counts against the signed-in user's daily request limit (1,000 a day), so no polling and no
  fetch-on-every-render. "Logins today" is fetched once per page load.
- A customer with no ACTIVE account (SUSPENDED, CLOSED, INACTIVE, DORMANT) is refused at sign-in by the backend (403); show its message as is.
- Irreversible or side-effecting calls (close account, Generate statement which emails/SMSes) run only on an explicit user action.
- After a change, run `npx tsc --noEmit` and `npx eslint <changed files>`. Update the matching doc in `.claude/docs/` (and `README.md` if a
  screen, route or env var changed) in the same commit.
- Do not commit `.env.local` (gitignored). The root `AGENTS.md` is generated by `next dev`: leave it out unless asked. `CLAUDE.md` is ours
  (project rules and the commit checklist): update it when a rule or workflow changes.


## Before you commit

1. `npx tsc --noEmit` and `npx eslint` on the changed files pass, and the e2e specs you affected pass (mind the daily request limit; see the `e2e` skill).
2. The matching doc in `.claude/docs/` and skill in `.claude/skills/` still match the code; `README.md` updated for any screen, route, env var, rule or
   spec change; `CLAUDE.md` updated if a project rule or workflow changed.
3. New screens are in `e2e/mobile.spec.ts` (every screen must fit a 320px phone).
4. Server-only code is not imported into client components; no secrets in logs or responses.
5. Only the files you meant to change are staged.
